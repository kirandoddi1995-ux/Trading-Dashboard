## Peak calculation, not an estimate-based rewrite permission

`Capacity` needs fresh timezone-aware measurement, cluster allocation, physical
free disk, reserved concurrent growth and physical reserve. `Allocation` needs
reviewed additional database and physical-disk UPPER BOUNDS including indexes,
TOAST, scratch and WAL. Unknown bounds block. A small `pg_column_size` sum is not
a bound for a new table/index nor a bloat percentage. Future savings never offset
transient allocation. Physical disk can be ample while the database quota is not.
Measurements older than 60 seconds or from the future block the plan.

At the owner's supplied 456,260,405-byte cluster reading, only 19,739,595 bytes
remain above the existing 24 MB floor, before concurrent growth. A hypothetical
162 MB additional copy (two times the observed ~81 MB quotes relation) exceeds
that margin. This is an offline arithmetic illustration, not a fresh DB reading,
not a validated exact rewrite estimate and not a compaction command.

The actual transaction admission/reservation adapter must serialize all writers,
recheck allocation and reserve reviewed worst-case increments; a pure plan or
advisory lock used by only one job is not enforcement. The owner-supplied 14-day
runway excludes other modes, allocation jumps and archive/metadata growth and is
not a deadline on which to rely.

## Partition retirement contract

Built-in date-range partitions are the preferred future physical-retention tool
for append-only quotes/scanner/volumes where global uniqueness/references permit
it. Do NOT partition the ledger first: signed aggregate chains/hot heads and
archived retries require their existing segment/catalog protocol. Do not force
all sources into a common retention window. Small immutable headers/active control
rows remain separately protected.

`retirement_plan()` checks half-open timezone-aware intervals against explicit
retention cutoff, fresh active-reference/unresolved-delivery counts and archive,
second-copy, restore and inventory receipt references. Missing/unknown protection
blocks. A partition crossing the retained boundary stays hot. All signatures,
source locks and actual deletion authority still remain false even when every
reference exists: the next adapter must authenticate receipts, identify exact
source rows/schema, compare roots/generations and recheck dependencies under lock.

Postgres cannot convert an ordinary table into a partitioned table in place.
Parent primary/unique keys must include every partition-key column; don't quietly
change existing global quote/observation identity. Foreign keys, historical joins,
RLS/grants on parent AND direct partition access, archived retries and partition
creation-before-writes need explicit design/tests. No permissive default partition
should hide failed lifecycle scheduling. Dropping/detaching needs reviewed lock
timeouts and race tests. No SQL DROP/DETACH is generated by this package.

## Verified documentation and decisions (8 Oct)

Free-project database allocation and physical disk/WAL are distinct limits;
organization average-size fair-use restrictions can also outlast a current size
reduction. Check both owner dashboards before eventual commissioning.
[Supabase database-size documentation](https://supabase.com/docs/guides/platform/database-size).

Ordinary vacuum allows reuse but normally does not return most allocation;
rewrite needs extra space and exclusive table access.
[Postgres vacuum documentation](https://www.postgresql.org/docs/17/routine-vacuuming.html).

pg_repack is supported by Supabase with client `-k`, but it is not a zero-space
solution; primary/unique-not-null identity and compatible extension/client versions
are prerequisites. Its documentation calls for additional physical space about
twice table-plus-index size. No extension is installed and no command is prepared
as executable owner approval here.
[Supabase pg_repack guide](https://supabase.com/docs/guides/database/extensions/pg_repack),
[pg_repack documentation](https://reorg.github.io/pg_repack/).

Range partition expiry avoids row-by-row high-water allocation, but its conversion,
uniqueness and locking restrictions require reviewed adapters.
[Postgres partitioning](https://www.postgresql.org/docs/17/ddl-partitioning.html).

Small inline raw JSON need not be compressed by default. Changing TOAST compression
does not by itself rewrite existing values or deduplicate repeated payloads.
[Postgres TOAST](https://www.postgresql.org/docs/17/storage-toast.html).

The Supabase changelog was inspected: the text/markdown endpoint could not be
fetched by the browsing tool, so its HTML changelog was used. Upcoming changes to
default API exposure are a reason not to rely on public-table defaults for new
storage tables. Use explicit private roles/grants/RLS, not automatic exposure.
[Supabase changelog](https://supabase.com/changelog).
